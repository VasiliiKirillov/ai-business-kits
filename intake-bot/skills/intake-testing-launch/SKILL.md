# Тесты, запуск, мониторинг

## Когда использовать

Бот собран и настроен (`intake-bot-build`), нужно убедиться, что он работает, и выпустить его к клиентам. Также когда бот "молчит" или что-то сломалось после запуска.

## Что нужно от человека

- Telegram-аккаунт для роли клиента и доступ к группе менеджера.
- Если есть второй человек для роли менеджера, хорошо; если нет, владелец нажимает кнопки сам.
- Решение владельца о запуске после проверки чеклиста.

## Шаги

Перед каждым шагом объясни человеку, что делаешь и зачем, одной-двумя фразами.

### 1. Автоматические сценарии (без ключей и сети)

```bash
cd ~/intake-bot && .venv/bin/python tests/run_scenarios.py
```

Это "ненастоящий мессенджер" с имитацией LLM. Прогоняет `tests/scenarios/<имя-конфига>/*.yaml`, печатает диалог, PASS или FAIL по каждому, возвращает код 1 при ошибках. Обязательные сценарии: полная бронь, позиция занята и предложены альтернативы, только вопрос (карточки нет), жалоба (карточка только с кнопкой "Отвечу сам"), спам (бот молчит), мат в адрес бота не жалоба, отказ от телефона дважды, клиент игнорирует вопрос, подтверждение менеджером, когда позиция уже занята.

### 2. Свои сценарии

Положи файл в `tests/scenarios/<имя-конфига>/<название>.yaml`. Формат строго как в `tests/run_scenarios.py`. Шаг: `client` (+ `parse`, что "вернул" парсер), `photo`, `manager: confirm | {own: текст}` или `seed` (занять позицию). Проверки шага: `expect_bot`, `expect_not_bot`, `expect_silent`, `expect_card`, `expect_buttons`, `expect_manager`, `expect_booking` (true или поля), `expect_no_booking`, `expect_document`, `expect_doc_contains`, `expect_photo`, `expect_no_photo`, `expect_forward_before_card`, `expect_fields`. На верхнем уровне: `config`, `name`, `seed_bookings`, `photos`, `steps`. Ключи в `parse` и названия позиций бери из своего конфига.

Прокат (по дням):

```yaml
config: config/business.yaml
name: "прокат: полная бронь с подтверждением"
seed_bookings: []              # занятые позиции для сценария "занято"
steps:
  - client: "привет, нужна <позиция> с 2030-12-01 на 3 дня"
    parse: {type: request, item: "<Название позиции>", date_from: "2030-12-01", days: 3}
    expect_bot: ["Скажи цену"]       # подстрока в ответе (мок возвращает статус)
  - client: "+66 00 000 0000"
    parse: {phone: "+66 00 000 0000"}
  - photo: {doc_full_name: "IVAN TESTOV", doc_number: "000000000", doc_nationality: "Russia", doc_birth_date: "1990-02-01"}
  - client: "да"
    parse: {confirmed: true}
    expect_card: true
  - manager: confirm
    expect_manager: ["BK-"]
    expect_booking: true
    expect_document: true
```

Запись на время (slots), без документа:

```yaml
config: config/business.yaml
name: "запись: дата, время, подтверждение"
steps:
  - client: "хочу на маникюр с покрытием в пятницу в 14:00"
    parse: {type: request, item: "Маникюр с покрытием", date: "2030-12-06", time: "14:00"}
    expect_bot: ["Скажи цену"]
  - client: "+7 000 000 00 00"
    parse: {phone: "+7 000 000 00 00"}
  - client: "да, верно"
    parse: {confirmed: true}
    expect_card: true
  - manager: confirm
    expect_booking: {item: "Маникюр с покрытием", start: "2030-12-06T14:00"}
    expect_document: false
```

Даты ставь далеко в будущем (2030), чтобы они не стали прошлым. Данные только выдуманные.

### 3. Консоль с настоящей LLM

```bash
.venv/bin/python -m intake --console
```

Команды: `/confirm`, `/own <текст>`, `/photo <путь>`, `/reset`, `/quit`. Здесь проверяется, как настоящая модель понимает живую речь и выдерживает тон. Прогони диалоги и покажи владельцу.

### 4. Живой тест в Telegram

Запусти бота (локально `.venv/bin/python -m intake` или на сервере через systemd) и пройди чеклист, отмечая каждый пункт:

- [ ] Счастливый путь: заявка от начала до карточки, нажатие "Подтвердить", бронь в таблице, документ создан, клиент получил подтверждение.
- [ ] Только вопрос ("сколько стоит ...", "до скольки работаете"): бот отвечает по сути, карточки нет.
- [ ] Жалоба: карточка менеджеру только с кнопкой "Отвечу сам".
- [ ] Спам (реклама): бот молчит.
- [ ] Грубый клиент: мат в адрес бота не считается жалобой, бот спокоен.
- [ ] Клиент игнорирует вопрос: бот два ответа не давит, потом спрашивает другими словами.
- [ ] Отказ дать телефон: бот один раз объясняет, на второй отказ пропускает.
- [ ] Занятая позиция: бот называет факт и предлагает альтернативы.
- [ ] Дата в прошлом: бот не принимает ее и спрашивает снова.
- [ ] Фото документа: бот читает данные (если модель умеет изображения), фото уходят менеджеру вместе с карточкой, а не посреди диалога.
- [ ] Менеджер нажимает "Подтвердить": карточка отмечается "подтверждено".
- [ ] Двойной клик по кнопке: вторая попытка отвечает "Уже обработана", брони не дублируются.
- [ ] Кнопка "Отвечу сам": следующее сообщение менеджера в группе уходит клиенту дословно.
- [ ] Выдуманное: спроси про характеристику, которой нет в каталоге: бот не придумывает, а предлагает уточнить у менеджера.
- [ ] Другой язык: ответ на языке клиента.

### 5. Чеклист перед запуском

- [ ] Google-приложение в Production, `google_token.json` свежий (если Google).
- [ ] `.env` с правами `600`, токены не в репозитории.
- [ ] Сервис включен и работает: `systemctl --user is-enabled intake-bot`, `is-active`, `loginctl show-user <user> | grep Linger=yes`.
- [ ] Логи чистые: `journalctl --user -u intake-bot -n 100` без ошибок.
- [ ] Группа менеджера верная, `MANAGER_CHAT_ID` ведет туда, а не в тестовую.
- [ ] Цены в боте совпадают с источником данных (сверь 3-5 позиций вручную).
- [ ] Приветствие и тон одобрены владельцем.
- [ ] Тестовые данные очищены (шаг 6).

### 6. Чистка тестовых данных

Урок: всегда чисти тестовые прогоны, иначе позиции остаются "занятыми", а таблица и Drive засоряются.

```bash
.venv/bin/python tools/cleanup_test_data.py            # показывает тестовые брони и документы
.venv/bin/python tools/cleanup_test_data.py --apply    # отменяет и удаляет
```

Скрипт отменяет брони, где клиент содержит "TEST" или созданные раннером, и удаляет тестовые документы. Спроси согласие перед удалением и проверь результат: таблица без тестовых строк, `output/` без тестовых файлов, Drive без тестовых копий.

### 7. Демо-повтор для записи экрана

Если владелец (или автор ролика) хочет показать бота в записи:

- Прогони сценарий через консоль (`.venv/bin/python -m intake --console`) с заготовленными репликами.
- Или заново отправь карточку в группу тестовой бронью и нажми кнопку на камеру.
- После записи сделай чистку (шаг 6). Не показывай на камере токены, `.env`, настоящие данные клиентов.

### 8. Мониторинг и "бот молчит"

Основные команды:

```bash
systemctl --user status intake-bot
journalctl --user -u intake-bot -n 100 --no-pager
journalctl --user -u intake-bot -f
```

Диагностика, если бот молчит:

1. Сервис жив? `systemctl --user is-active intake-bot`. Нет: смотри логи, перезапусти.
2. В логах ошибки LLM `401`, `403`, `invalid api key`: проверь `LLM_API_KEY`, баланс у провайдера и что ключ официальный API, а не подписка ([shared/llm-providers](../../../shared/llm-providers/SKILL.md)).
3. Таймауты или "country not supported": геоблок, прокси и смена региона описаны в [shared/llm-providers](../../../shared/llm-providers/SKILL.md).
4. Ошибка `invalid_grant` от Google: токен протух (в режиме Testing он живет 7 дней), лечение в [shared/google-workspace](../../../shared/google-workspace/SKILL.md): опубликовать в Production и заново запустить `.venv/bin/python tools/google_auth.py`. Брони тем временем не пишутся в таблицу, менеджер видит "не смог ...".
5. Бот отвечает, но карточки не приходят: неверный `MANAGER_CHAT_ID`, бота убрали из группы или у группы изменился id (после превращения в супергруппу). Снова `/id` в группе.
6. После правки кода ничего не изменилось: забыл `systemctl --user restart intake-bot`.
7. Нехватка памяти на VPS: `free -m`, смотри `dmesg | grep -i oom`.

## Проверка

- `.venv/bin/python tests/run_scenarios.py`: все PASS.
- Все пункты живого теста отмечены.
- Чеклист запуска полностью закрыт.
- `cleanup_test_data.py` ничего больше не находит.
- Владелец явно сказал "запускаем".
- В `~/intake-bot/intake-progress.md` записано: дата запуска, что где лежит (без секретов), как перезапускать.

## Подводные камни

- Тестовые брони занимают емкость: позиции кажутся занятыми. Чисти после каждого прогона.
- Тестируй не только счастливый путь: основные поломки в диалогах с игнорированием вопросов и отказами.
- Не показывай настоящие данные клиентов в записи экрана.
- Не запускай бота на два экземпляра с одним токеном: Telegram вернет конфликт. Локальный тестовый запуск и серверный не должны работать одновременно.
- Google Testing-режим: бот работает неделю и ломается. Проверь до запуска.
- Если менялся конфиг, перезапусти сервис, иначе бот работает по старому.
- Рассказывай владельцу, где смотреть логи и как перезапускать: он не должен зависеть от тебя при простой проблеме.

## Дальше

Бот запущен. Предложи владельцу:

- новые каналы (WhatsApp через новый адаптер мессенджера);
- настройку тона по реальным диалогам через неделю;
- резервную копию `*.db` и `.env`;
- периодически проверять логи и баланс у провайдера LLM.
